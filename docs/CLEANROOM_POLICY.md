# Hetu 洁净室研发纪律（Cleanroom Policy v1.0）

目的：使 Hetu 的独立性成为**可举证的工程事实**，而非口头声明。本纪律对全部贡献者
（人类与 AI Agent）生效，违反即视为污染，相关提交隔离重做。

2026-11-18 桌面范围说明。按产品要求，`packaging/macos/hasu_port/` 显式接纳带来源声明的 前作前端移植。桌面移植与对接不计入初始洁净室证据。内核的六步纪律继续适用。

## 六步纪律（对应方案第四节）

1. **规范先行**：实现只能以 `docs/FUNCTIONAL_SPEC.md` 及其修订为输入。规范只允许来自
   使用需求、公开功能描述、合法观察到的输入输出行为。旧产品源码不是规范来源。
2. **隔离实现**：实现人员/编码 Agent 在工作本仓库期间**禁止读取** 旧产品源码树
   （旧产品产品树、检出目录与运行时源码）。审读上游源码者只参与
   需求界定，不写实现码。本仓库初始实现的执行记录：实现过程未打开任何上游源码文件。
3. **独立架构**：模块与数据模型从任务执行、持久状态、错误恢复、工具权限、记忆管理、
   多模型路由重新定义（见 ADR-0001），禁止逐文件逐类映射上游结构。
4. **独立测试**：测试为自研反例驱动夹具（tests/），未迁移任何上游测试文件。
5. **证据留存**：设计版本、提交记录、依赖清单、AI 输入来源、相似性检查、人工审核
   结果全程落盘于 `docs/evidence/` 与 git 历史。
6. **法律与依赖审核**：确认无受保护内容复制 + 全部代码权利链完整后，才讨论独立许可
   选择（当前意向：MIT，见 RIGHTS_CHAIN.md）。

## 相似性扫描（发布前必做）

- 发布前对上游发行版跑 token/AST 相似性扫描（如 jPlag/tokmatch 或等价工具），
  结果存入 `docs/evidence/similarity/`。初始扫描：待发布窗口执行（见 README 发布清单）。

## 红线（继承方案第七节）

不搬图引擎 / 不建 Temporal server / 不建第二调度器 / 不做记忆双源 / LLM 自评不作结论 /
不引 AutoGen 依赖 / telemetry 不外发 / 进化体不得修改评分器与保护机制 / 禁止假通过 /
不做免审批动态委派 / 压缩永不删除原文。
